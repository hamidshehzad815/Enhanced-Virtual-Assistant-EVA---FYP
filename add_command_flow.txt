================================================================

  Intent naming:
    Pipeline/router/handler return: scheduling_add
    Redis pending_action.intent: "add" (not scheduling_add)

  Handler order (handlers/scheduling/add.py):
    task_name → date (Duckling) → duration + priority defaults
    → time (or behavioral suggestion) → past datetime check
    → quiet hours (yes_no) → owner time overlap (409 conflict, no Redis)
    → duplicate (yes_no) → collaborators → insert task

  Behavioral time suggestion thresholds (user_settings):
    analytics_min_tasks_threshold default 20 (not 10)
    analytics_min_tasks_per_day default 5
    Uses productivity_scorer (get_scheduling_suggestion), not raw countDocuments only

  Extra pending states (no stage field for add):
    pending_reason: time_suggestion | time_suggestion_fallback | past_datetime
      | quiet_hours | duplicate
    suggested_range + suggested_time for number prompt
    quiet_hour_matches on Redis for quiet-hours yes_no

  Terminal statuses: pending | success | cancelled | conflict | validation_error

  Collaborators: max 2; lookup by username OR display name; friend required;
    collaborator busy → conflict (collaborator_busy)

  Notifications: owner task_scheduled (in_app, email);
    each collaborator collaboration_invite (push, in_app, email)

  Google Calendar: create_event if google_calendar integration active;
    stores google_calendar_event_id on task (non-blocking)

PIPELINE (inside AI Server)
================================================================

  REQUEST RECEIVED FROM NODE.JS
  {
    message, user_id, session_id,
    input_type, timestamp
  }
  ↓
  AI SERVER SELF-FETCH (before pipeline runs)
  → db.users.findOne({ _id: user_id })
  → db.user_settings.findOne({ user_id })
  → db.conversation_history.find({ session_id }).limit(10)
  → db.integrations.find({ user_id, is_active: true })
  → Redis GET context:{user_id}
  ↓
  PREPROCESSING
  → convert to lowercase
  → remove punctuation
  → fix spelling errors
  → too_short check → Gemini: "Could you be more specific?"
                    → return to Node.js → stop
  ↓
  CONTEXT MANAGER
  → check fetched Redis state
  → pending exists? → handle reply → stop or continue
  → no pending → continue to Model 1
  ↓
  MODEL 1 — Input Type Classifier
  → general          → Gemini generates greeting/help reply
  → out_of_scope     → Gemini: friendly out of scope reply
  → confirmation     → Gemini: "not expecting a reply now"
  → multiple_command → Gemini: "one request at a time"
  → command          → continue
  ↓
  MODEL 2 — Intent Classifier
  → output: scheduling_add
  ↓
  NER — runs on ORIGINAL cased text
  → extracts only add-relevant entities:
    {
      task_name   : "Physics exam",
      date        : "Monday",
      time        : "5PM",
      priority    : "high",
      duration    : "2 hours",
      collaborator: "Ahmed"
    }
  ↓
  ENTITY SCOPING
  → keep : task_name, date, time, duration,
           priority, collaborator
  → drop : anything else NER may have extracted
  ↓
  HANDLER — handlers/scheduling/add.py

================================================================
STEP 2 — DATE RESOLUTION
================================================================

  → pass entities["date"] to Duckling (AI server calls direct)
  → Duckling returns ISO datetime + grain

    "Monday"     → 2026-03-23T00:00:00  grain: day
    "tomorrow"   → 2026-03-17T00:00:00  grain: day
    "25th March" → 2026-03-25T00:00:00  grain: day
    "next week"  → 2026-03-23T00:00:00  grain: week

  → store date_part = YYYY-MM-DD
  → continue to STEP 3

================================================================
STEP 3b — PAST DATETIME / QUIET HOURS / OWNER OVERLAP (implemented)
================================================================

  Past due_datetime (same day → re-ask time; other day → re-ask date):
    pending_reason: past_datetime

  Quiet hours (settings.quiet_hours[] or legacy start/end):
    expected_response: yes_no, pending_reason: quiet_hours
    yes → allow_quiet_hours_override; no → strip time, re-ask time

  Owner or accepted-collaborator overlap at same slot:
    status: conflict — no Redis; Gemini action task_time_conflict

STEP 11 — GENERATE GEMINI RESPONSE
================================================================

  AI server builds prompt with full context:
  {
    system_instruction:
      "You are EVA, a friendly and intelligent academic assistant.
       Generate a short, warm, specific reply based ONLY on what
       just happened. Use the user's name. Mention the task name,
       date, time naturally. Be conversational, not robotic.
       Never use generic phrases like 'Task added successfully'.
       Max 2 sentences. Vary phrasing each time.",

    action_context: {
      action           : "task_added",
      username         : "Ali",
      task_name        : "Physics exam",
      date             : "Monday 23rd March",
      time             : "5PM",
      priority         : "high",
      collaborator     : "Ahmed" or null,
      calendar_synced  : true or false,
      scheduled_by     : "manual" or "behavioral_analytics"
    }
  }

  Gemini returns unique natural reply. Examples:

  Basic task added:
  "Done Ali! Physics exam is scheduled for Monday at 5PM —
   I'll remind you 30 minutes before."

  With collaborator:
  "Physics exam is locked in for Monday at 5PM, Ali.
   I've sent Ahmed a collaboration invite as well."

  Behavioral suggestion accepted:
  "Perfect Ali — Physics exam set for Monday at 6PM,
   your most productive time on Mondays."

  Calendar synced:
  "Physics exam is on for Monday at 5PM and it's been
   added to your Google Calendar too, Ali."
