CONTEXT MANAGER — ADD COMMAND (FINAL)
Runs inside AI Server — Redis managed by AI Server directly
================================================================

DECISIONS LOCKED
================================================================

  1. Context manager runs BEFORE Model 1 on every input
  2. Redis state fetched by AI server at request start
     (part of self-fetch — same as user info, settings)
  3. Hybrid approach based on expected_response type:
       free_text → skip Model 1, handle reply directly
       yes_no    → run Model 1 first, then handle
       number    → run Model 1 first, then handle
  4. Missing entities asked ONE BY ONE in order:
       task_name → date → time
  5. After every valid reply, handler re-entered from STEP 1
  6. Cancel checked FIRST before anything else
  7. All Gemini replies are natural and specific to context
  8. AI server reads/writes Redis directly
  9. All DB validation queries done by AI server directly
  10. TTL = 300 seconds, reset on every Redis write


================================================================
REDIS STATE STRUCTURE
================================================================

  Key    : "context:{user_id}"
  Value  : JSON string
  TTL    : 300 seconds, reset on every write
  Managed by: AI Server directly

  {
    expected_response : "free_text" | "number" | "yes_no",
    missing_entity    : "task_name" | "date" | "time" | null,
    suggested_time    : "18:00",  ← only in number state
    pending_action    : {
      intent   : "add",
      entities : { ...collected so far... }
    }
  }

  NOTE: Redis state is fetched at the start of every
  AI server request as part of self-fetch, not on-demand
  inside the context manager.

================================================================
CONTEXT MANAGER DECISION FLOW
================================================================

  Input arrives at AI server
       ↓
  PREPROCESSING
  → lowercase, punctuation removal, spelling fix
  → too_short check → Gemini reply → STOP if too short
       ↓
  Redis state already fetched (from AI server self-fetch)
       │
       ├── NO pending state
       │   → pass to Model 1 normally
       │
       └── pending state EXISTS
               ↓
           CHECK CANCEL FIRST
           trigger words:
           cancel / stop / abort / never mind /
           forget it / forget that / leave it /
           discard / no cancel
               │
               ├── YES
               │   → AI server clears Redis (DEL key)
               │   → Gemini generates natural cancellation:
               │     "No problem Ali, I've cancelled that
               │      for you."
               │   → return to Node.js → STOP
               │
               └── NO
                     │
                     ├── expected = free_text
                     │     → SKIP Model 1 entirely
                     │     → handle reply directly
                     │       (see free_text states below)
                     │
                     ├── expected = yes_no
                     │     → RUN Model 1 on processed text
                     │     → route based on result
                     │       (see yes_no handling below)
                     │
                     └── expected = number
                           → RUN Model 1 on processed text
                           → route based on result
                             (see number handling below)


================================================================
FREE TEXT STATE HANDLING
================================================================

  Why Model 1 skipped:
  Replies like "Physics exam" or "6PM" have no command
  structure. Model 1 would misclassify them. We know
  exactly what we are waiting for from Redis state.
  Handle directly without classification.


STATE 1 — missing: task_name
────────────────────────────────────────────────────────────

  User replies: anything

  → take ENTIRE reply as task_name
  → no parsing, no validation needed
  → merge into pending_action.entities
  → AI server clears Redis
  → re-enter handler from STEP 1
  → handler now has task_name → checks date next
  → Gemini will ask for date naturally:
    "Got it — when should I schedule the Physics exam?"


STATE 2 — missing: date
────────────────────────────────────────────────────────────

  User replies: "Monday" / "25th March" / "next week"

  → pass reply to Duckling (AI server calls direct)
  → Duckling resolves:
      merge resolved ISO date into pending_action.entities
      AI server clears Redis
      re-enter handler from STEP 1
      handler has task_name + date → checks time next

  → Duckling fails:
      AI server keeps Redis (TTL resets)
      Gemini generates natural validation error:
      "I didn't quite catch that date — could you say
       something like 'Monday' or '25th March', Ali?"
      STOP — return to Node.js


STATE 3 — missing: time (no behavioral data)
────────────────────────────────────────────────────────────

  User replies: "5PM" / "18:00" / "evening"

  → pass reply to Duckling (AI server calls direct)
  → Duckling resolves:
      merge resolved time into pending_action.entities
      scheduled_by = "manual"
      AI server clears Redis
      re-enter handler from STEP 1
      handler has all three → continues to STEP 2

  → Duckling fails:
      AI server keeps Redis (TTL resets)
      Gemini generates natural validation error:
      "That time didn't work for me — try something like
       '5PM' or '18:00', Ali."
      STOP — return to Node.js


================================================================
NUMBER STATE HANDLING
================================================================

  Why Model 1 runs first:
  "1" could be part of another command in edge cases.
  Model 1 confirms it is a confirmation intent first.


STATE 4 — behavioral suggestion shown
────────────────────────────────────────────────────────────

  Model 1 runs on processed text:

    → command / multiple_command detected:
        AI server keeps Redis (TTL resets)
        Gemini: "I'm still waiting on your choice, Ali.
                 Say cancel if you'd rather start over."
        STOP

    → general / out_of_scope detected:
        AI server keeps Redis (TTL resets)
        Gemini: "Just reply with 1 or 2, Ali."
        STOP

    → confirmation detected → proceed:

  User reply = "1":
  → use suggested_time from Redis
  → merge as time into pending_action.entities
  → scheduled_by = "behavioral_analytics"
  → AI server clears Redis
  → re-enter handler from STEP 1
  → handler has all three → continues to STEP 2

  User reply = "2":
  → user wants to enter time manually
  → AI server updates Redis:
      expected_response = "free_text"
      missing_entity    = "time"
      remove suggested_time field
  → Gemini: "Sure, what time works for you?"
  → STOP — next reply handled as STATE 3

  User reply = anything else:
  (confirmation detected but not 1 or 2)
  → AI server keeps Redis (TTL resets)
  → Gemini: "Just reply with 1 or 2, Ali."
  → STOP


================================================================
YES/NO STATE HANDLING
================================================================

  Why Model 1 runs first:
  "yes" could begin a command in edge cases.
  Model 1 confirms it is confirmation intent first.


STATE 5 — duplicate found
────────────────────────────────────────────────────────────

  Model 1 runs on processed text:

    → command / multiple_command detected:
        AI server keeps Redis (TTL resets)
        Gemini: "I'm still waiting on your answer, Ali.
                 Say cancel if you want to stop."
        STOP

    → general / out_of_scope detected:
        AI server keeps Redis (TTL resets)
        Gemini: "Just a yes or no will do, Ali."
        STOP

    → confirmation detected → proceed:

  User reply matches yes keywords:
  yes / yeah / yep / sure / go ahead / do it / confirm / ok
  → AI server clears Redis
  → re-enter handler from STEP 1
  → handler has all entities → continues to STEP 2

  User reply matches no keywords:
  no / nope / nah / reject
  → AI server clears Redis
  → Gemini: "No problem, nothing was added."
  → STOP — return to Node.js

  User reply = anything else:
  (confirmation detected but no keyword match)
  → AI server keeps Redis (TTL resets)
  → Gemini: "Just a yes or no will do, Ali."
  → STOP


================================================================
CROSS CUTTING CASES
================================================================

CANCEL — checked first, applies to ALL states
────────────────────────────────────────────────────────────
  Always checked before expected_response routing.
  trigger words:
  cancel / stop / abort / never mind / forget it /
  forget that / leave it / discard / no cancel

  → AI server clears Redis (DEL context:{user_id})
  → Gemini: "No problem Ali, I've cancelled that for you."
  → return to Node.js → STOP


NEW COMMAND WHILE PENDING — yes_no and number states only
────────────────────────────────────────────────────────────
  free_text states skip Model 1 entirely.
  Only applies when Model 1 runs.

  Model 1 returns command or multiple_command:
  → AI server keeps Redis (TTL resets)
  → Gemini: "I'm still waiting on your reply, Ali.
             Say cancel if you'd like to start fresh."
  → STOP


TTL EXPIRY — all states
────────────────────────────────────────────────────────────
  User silent for 300 seconds
  → Redis key auto-expires
  → AI server finds no pending state on next request
  → pipeline starts fresh
  → no message, no action needed


================================================================
GEMINI REPLY GUIDELINES FOR CONTEXT MANAGER
================================================================

  All follow-up questions and error replies must be:
  → Natural and conversational, not robotic
  → Specific — mention task name where relevant
  → Use the user's name (fetched from DB at request start)
  → Short — one sentence where possible
  → Never say "Invalid input" or "Error" to the user
  → Vary phrasing — do not repeat the same question
    if user has already been asked once

  Examples of WRONG replies (never use these):
  × "Invalid date format. Please try again."
  × "Task name is required."
  × "Please enter a valid time."

  Examples of CORRECT replies (what Gemini generates):
  ✓ "I didn't quite catch that date — try something like
     'Monday' or '25th March', Ali."
  ✓ "What time works best for the Physics exam?"
  ✓ "What would you like to call this task, Ali?"

================================================================
HANDLER RE-ENTRY RULE
================================================================

  After every valid reply:
  → entities merged into pending_action.entities
  → AI server clears Redis
  → handler re-entered from STEP 1

  Handler checks every time from top:
    task_name missing? → Gemini asks → STOP
    date missing?      → Gemini asks → STOP
    time missing?      → STEP 3 handles → STOP or continue
    all present?       → continue to STEP 2

  Handler never needs to know which step it was on.
  It re-evaluates with what it currently has.
