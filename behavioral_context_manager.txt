================================================================
CONTEXT MANAGER — BEHAVIORAL COMMAND (FINAL)
Runs inside AI Server — Redis managed by AI Server directly
================================================================

CORE DECISION
================================================================

  Behavioral command sets ONLY ONE possible pending state.

  The only case where behavioral needs a follow-up is when
  sub-intent is "best_time_for_day" and the user did not
  specify which day.

  Example:
    "find the best time for me"     → day missing → ask
    "when should I schedule"        → day missing → ask
    "find the best time on Monday"  → day present → no ask

  All other sub-intents (productive_hours, productive_days,
  completion_rate, productivity_report) never need a
  follow-up — they either have enough data or they don't.

  Compare with add (3 required entities, 5 states) and
  delete (4 match cases, bulk confirm). Behavioral is
  the simplest command in the context manager.


================================================================
REDIS STATE STRUCTURE FOR BEHAVIORAL
================================================================

  Key    : "context:{user_id}"
  TTL    : 300 seconds

  Only one possible state:

  {
    expected_response : "free_text",
    pending_action    : {
      intent     : "behavioral",
      sub_intent : "best_time_for_day",
      entities   : {}
    }
  }


================================================================
PENDING STATE — best_time_for_day, day missing
================================================================

  When sub-intent = "best_time_for_day" and no day entity:

  → AI server writes Redis:
    {
      expected_response : "free_text",
      pending_action    : {
        intent     : "behavioral",
        sub_intent : "best_time_for_day",
        entities   : {}
      }
    }

  → Gemini:
  EVA: "Which day would you like me to find
        the best time for, Ali?"

  → STOP

  User replies: "Monday" / "next Friday" / "Tuesday"

  → Context manager intercepts (free_text → skip Model 1)
  → treat reply as day value
  → merge into pending entities
  → clear Redis
  → re-enter behavioral handler from STEP 1
  → handler now has day → runs best_time_for_day query


================================================================
CONTEXT MANAGER DECISION FLOW FOR BEHAVIORAL
================================================================

  Input arrives at AI server
       ↓
  PREPROCESSING
       ↓
  Redis check (from self-fetch)
       │
       ├── NO pending state
       │   → pass to Model 1 normally
       │
       └── pending state EXISTS
               ↓
           CHECK CANCEL FIRST
           cancel / stop / never mind / forget it
               │
               ├── YES
               │   → clear Redis
               │   → Gemini: "No problem, never mind."
               │   → STOP
               │
               └── NO
                     │
                     └── expected = free_text
                           → SKIP Model 1
                           → treat reply as day value
                           → validate: is it a weekday?
                               │
                               ├── valid day
                               │   → merge into entities
                               │   → clear Redis
                               │   → re-enter handler
                               │
                               └── not a valid day
                                   → Redis stays (TTL resets)
                                   → Gemini: "I didn't catch
                                     that — which day did you
                                     mean, Ali? Like Monday
                                     or Friday."
                                   → STOP


================================================================
DAY VALIDATION
================================================================

  Valid day values (case insensitive):
  monday, tuesday, wednesday, thursday,
  friday, saturday, sunday

  On reply:
  → lowercase the reply
  → check if any valid day name is present in reply
  → "next Monday" → extract "monday" → valid
  → "this Friday" → extract "friday" → valid
  → "tomorrow"    → not a weekday name → invalid
  → "5PM"         → not a weekday → invalid

  NOTE: Duckling is NOT used here. Day is just a weekday
  name, not a full date. Duckling resolves "Monday" to
  a specific ISO date — we do not need that for analytics.
  We just need the weekday number (0-6).


================================================================
WHY NO MORE STATES
================================================================

  productive_hours  → returns data or "not enough data" reply
                     → no follow-up ever needed

  productive_days   → same, no follow-up

  completion_rate   → same, no follow-up

  productivity_report → same, no follow-up

  best_time_for_day → ONLY case needing follow-up
                     → only when day missing from input
                     → one free_text state, done


================================================================
CROSS CUTTING CASES
================================================================

CANCEL
────────────────────────────────────────────────────────────
  Only applies when best_time_for_day state is pending.

  → clear Redis
  → Gemini: "No problem, never mind."
  → STOP


NEW COMMAND WHILE PENDING
────────────────────────────────────────────────────────────
  free_text state skips Model 1.
  New command detection does not apply here.
  If user sends "add physics exam on Monday at 5PM"
  while behavioral pending → context manager treats the
  entire reply as a day value → day validation fails →
  ask again naturally.

  This is acceptable because:
  → behavioral pending state TTL = 300s
  → if user genuinely wants a new command they can say
    "cancel" first, then send the new command
  → the free_text state for behavioral only expects a
    single word (weekday name) so misclassification risk
    is low


TTL EXPIRY
────────────────────────────────────────────────────────────
  User silent for 300 seconds
  → Redis auto-expires
  → next input starts fresh
  → no message needed
