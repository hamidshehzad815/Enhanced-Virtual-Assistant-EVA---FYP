================================================================
CONTEXT MANAGER — LEARNING DELETE COMMAND (FINAL)
Runs inside AI Server — Redis managed by AI Server directly
================================================================

DECISIONS LOCKED
================================================================

  1. Context manager runs BEFORE Model 1 on every input
  2. Redis state fetched at request start (self-fetch)
  3. Hybrid approach based on expected_response:
       free_text → skip Model 1, handle reply directly
       yes_no    → run Model 1 first, then handle
       number    → run Model 1 first, then handle
  4. Cancel checked FIRST before anything else
  5. TTL = 300 seconds, reset on every Redis write
  6. Handler re-entered from STEP 1 after free_text reply
  7. Handler jumps to STEP 5 (deletion) after yes confirmed
  8. All Gemini replies natural, specific, use user name
  9. "cancel" keyword = flow cancellation not goal deletion


================================================================
REDIS STATE STRUCTURE FOR LEARNING DELETE

  Key    : "context:{user_id}"
  TTL    : 300 seconds

    pending_action    : {

      goals    : [ { title, roadmap_key, status,
                     completed_topics, total_topics } ... ],
      bulk     : true | false,

    }
  }

================================================================
CONTEXT MANAGER DECISION FLOW
================================================================

  Input arrives at AI server
       ↓
  PREPROCESSING (lowercase + too_short check)
       ↓
  Redis state already fetched (from self-fetch)
       │
       ├── NO pending state
       │   → pass to Model 1 normally
       │
       └── pending state EXISTS
               ↓
           CHECK CANCEL FIRST
           cancel / stop / abort / never mind /
           forget it / leave it / discard / no cancel
               │
               ├── YES
               │   → AI server clears Redis
               │   → EVA: "No problem Ali,
               │           nothing was deleted."
               │   → STOP
               │
               └── NO
                     │
                     ├── expected = free_text (State 1)
                     │     → SKIP Model 1
                     │     → handle reply directly
                     │
                     ├── expected = yes_no (State 2 or 4)
                     │     → RUN Model 1
                     │     → handle based on result
                     │
                     └── expected = number (State 3)
                           → RUN Model 1
                           → handle based on result


================================================================
FREE TEXT HANDLING — STATE 1
================================================================

  Why Model 1 skipped:
  Reply like "Python" or "Python basics" has no command
  structure. Model 1 would misclassify it. We know we
  are waiting for a goal identifier from Redis state.

  User replies: anything

  → pass reply through NER to extract topic + subtopic
  → topic not found in reply:
      Redis stays (TTL resets)
      EVA: "I didn't catch that. Which learning goal
            would you like to delete? Try saying
            something like 'Python' or 'MySQL', Ali."
      STOP

  → topic found:
      Validation — normalize via TOPIC_ALIAS_MAP
      check SUPPORTED_TOPICS
      not supported:
        clear Redis
        EVA: "I couldn't find a learning goal for
              [topic], Ali. Check the topic name
              and try again."
        STOP

      subtopic present → map via SUBTOPIC_ALIAS_MAP
                         + regex search
      → merge topic + subtopic into entities
      → AI server clears Redis
      → re-enter handler from STEP 1
      → handler queries DB with new entities


================================================================
YES/NO HANDLING — STATE 2 (single match confirm)
================================================================

  Why Model 1 runs first:
  "yes" could begin a new command. Model 1 confirms
  it is a confirmation intent first.

  Model 1 runs:

    → command / multiple_command:
        Redis stays (TTL resets)
        EVA: "I'm still waiting — want me to delete
              Python basics? Just yes or no, Ali."
        STOP

    → general / out_of_scope:
        Redis stays (TTL resets)
        EVA: "Just a yes or no will do, Ali."
        STOP

    → confirmation → proceed:

  YES keywords:
  yes / yeah / yep / sure / go ahead / do it / confirm / ok
  → AI server clears Redis
  → jump to STEP 5 of delete handler (perform deletion)
  → delete the single goal in goal_ids

  NO keywords:
  no / nope / nah / don't / leave it / keep it
  → AI server clears Redis
  → EVA: "No problem, I left Python basics
          as it is, Ali."
  → STOP

  Unrecognised:
  → Redis stays (TTL resets)
  → EVA: "Just a yes or no will do, Ali."
  → STOP


================================================================
NUMBER HANDLING — STATE 3 (multiple matches)
================================================================

  Why Model 1 runs first:
  "1" or "2" could be a topic name or other input.
  Model 1 confirms it is confirmation intent first.

  Model 1 runs:

    → command / multiple_command:
        Redis stays (TTL resets)
        EVA: "I'm still waiting for your choice.
              Say cancel to stop, Ali."
        STOP

    → general / out_of_scope:
        Redis stays (TTL resets)
        EVA: "Pick a number from the list, or
              say 'all', Ali."
        STOP

    → confirmation → proceed:

  Valid number (1 to N where N = len(goal_ids)):
  → get selected_goal = goals[number - 1]
  → update Redis:
      expected_response = "yes_no"
      goal_ids          = [ selected_goal_id ]
      goals             = [ selected_goal ]
      bulk              = false
  → EVA: "Got it — delete Python basics,
          active with 3 of 8 sessions done?"
  → STOP
  → next reply handled as State 2

  "all" keyword:
  trigger: "all" / "all of them" / "delete all" /
           "every one" / "all goals"
  → update Redis:
      expected_response = "yes_no"
      bulk              = true
      goal_ids and goals stay the same (all matches)
  → EVA: "Just to confirm — delete all 2
          Python goals? Completed sessions
          will be kept."
  → STOP
  → next reply handled as State 4

  Number out of range:
  → Redis stays (TTL resets)
  → EVA: "That number is not on the list, Ali.
          Pick between 1 and [N], or say 'all'."
  → STOP

  Anything else:
  → Redis stays (TTL resets)
  → EVA: "Pick a number from the list or say
          'all' to delete everything, Ali."
  → STOP


================================================================
YES/NO HANDLING — STATE 4 (bulk confirmation)
================================================================

  Same Model 1 routing as State 2.

  YES keywords:
  → AI server clears Redis
  → jump to STEP 5 of delete handler
  → bulk = true → delete ALL goal_ids in pending state
  → EVA: "Done Ali — all 2 Python goals have
          been removed. Your completed sessions
          are still saved."
  → STOP

  NO keywords:
  → AI server clears Redis
  → EVA: "No problem, I left all those goals
          as they are, Ali."
  → STOP

  Unrecognised:
  → Redis stays (TTL resets)
  → EVA: "Just a yes or no, Ali."
  → STOP


================================================================
CROSS CUTTING CASES (apply to ALL states)
================================================================

CANCEL — always checked first
────────────────────────────────────────────────────────────
  cancel / stop / abort / never mind / forget it /
  forget that / leave it / discard / no cancel

  NOTE: "cancel" here means cancelling the conversation
  flow — NOT deleting the goal. User must confirm
  deletion explicitly via yes/no flow.

  → AI server clears Redis
  → EVA: "No problem Ali, nothing was deleted."
  → STOP


NEW COMMAND WHILE PENDING — yes_no and number only
────────────────────────────────────────────────────────────
  (free_text state skips Model 1 — not applicable there)

  Model 1 returns command / multiple_command:
  → Redis stays (TTL resets)
  → EVA: "I'm still waiting for your reply, Ali.
          Say cancel if you want to start fresh."
  → STOP


TTL EXPIRY — all states
────────────────────────────────────────────────────────────
  User silent for 300 seconds
  → Redis auto-expires
  → next input starts pipeline fresh
  → no message needed
