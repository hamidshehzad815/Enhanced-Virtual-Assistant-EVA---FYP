================================================================
CONTEXT MANAGER — UPDATE COMMAND (FINAL)
Runs inside AI Server — Redis managed by AI Server directly
================================================================

DECISIONS LOCKED
================================================================

  1. Context manager runs BEFORE Model 1 on every input
  2. Redis state fetched at request start (self-fetch)
  3. Update has a TWO-PHASE flow reflected in Redis:
       stage = "identify"       → finding which task
       stage = "what_to_update" → asking what to change
       stage = "confirm"        → final yes/no before writing
  4. Hybrid approach (same as add/delete):
       free_text → skip Model 1, handle directly
       yes_no    → run Model 1 first
       number    → run Model 1 first
  5. Cancel checked FIRST before anything else
  6. TTL = 300 seconds, reset on every Redis write
  7. Handler re-enters from STEP 1 after free_text reply
  8. Handler jumps to STEP 8 (perform update) after yes
  9. All Gemini replies natural, specific, use user name


================================================================
REDIS STATE STRUCTURE FOR UPDATE
================================================================

  Key    : "context:{user_id}"
  TTL    : 300 seconds

  {
    expected_response : "free_text" | "number" | "yes_no",
    pending_action    : {
      intent   : "update",
      stage    : "identify" | "what_to_update" | "confirm",
      task_id  : null or identified task_id,
      task     : null or { title, due_datetime, priority },
      task_ids : [] or [ matched ids ] (for number state),
      tasks    : [] or [ matched task summaries ],
      entities : { ...all extracted entities so far... },
      updates  : {} or { fields and new values confirmed }
    }
  }


================================================================
ALL PENDING STATES FOR UPDATE COMMAND
================================================================

  State 1 — no identifier given (stage: identify)
  ────────────────────────────────────────────────────
  {
    expected_response : "free_text",
    pending_action    : {
      intent   : "update",
      stage    : "identify",
      task_id  : null,
      entities : { ...any update fields already found... }
    }
  }
  EVA asked: "Which task would you like to update, Ali?"


  State 2 — multiple matches found (stage: identify)
  ────────────────────────────────────────────────────
  {
    expected_response : "number",
    pending_action    : {
      intent   : "update",
      stage    : "identify",
      task_ids : [ "id1", "id2", "id3" ],
      tasks    : [
        { title: "Physics exam", due_datetime: "...",
          priority: "high" },
        { title: "Physics lab",  due_datetime: "...",
          priority: "medium" }
      ],
      entities : { ...all extracted entities... }
    }
  }
  EVA asked: "I found 3 tasks. Which one, Ali?
              1. Physics exam — Monday 5PM (high)
              2. Physics lab — Tuesday 3PM (medium)
              3. Physics quiz — Wednesday 2PM (low)"


  State 3 — task identified, no update field (stage: what_to_update)
  ────────────────────────────────────────────────────
  {
    expected_response : "free_text",
    pending_action    : {
      intent   : "update",
      stage    : "what_to_update",
      task_id  : "identified_task_id",
      task     : { title: "Physics exam",
                   due_datetime: "2026-03-23T17:00:00",
                   priority: "high" },
      entities : {}
    }
  }
  EVA asked: "What would you like to change about
              Physics exam, Ali? You can update the
              date, time, priority, status, or name."


  State 4 — update fields known, awaiting confirmation (stage: confirm)
  ────────────────────────────────────────────────────
  {
    expected_response : "yes_no",
    pending_action    : {
      intent   : "update",
      stage    : "confirm",
      task_id  : "identified_task_id",
      task     : { title: "Physics exam", ... },
      entities : { new_priority: "high" },
      updates  : { priority: "high" }
    }
  }
  EVA asked: "Change Physics exam priority to high, Ali.
              Confirm?"


================================================================
CONTEXT MANAGER DECISION FLOW
================================================================

  Input arrives at AI server
       ↓
  PREPROCESSING (lowercase + too_short check)
       ↓
  Redis state already fetched (from self-fetch)
       │
       ├── NO pending state
       │   → pass to Model 1 normally
       │
       └── pending state EXISTS
               ↓
           CHECK CANCEL FIRST
           cancel / stop / abort / never mind /
           forget it / leave it / discard / no cancel
               │
               ├── YES
               │   → AI server clears Redis
               │   → Gemini: "No problem Ali,
               │              nothing was changed."
               │   → STOP
               │
               └── NO
                     │
                     ├── expected = free_text
                     │   (State 1 or State 3)
                     │     → SKIP Model 1
                     │     → route by stage (see below)
                     │
                     ├── expected = number (State 2)
                     │     → RUN Model 1
                     │     → handle (see below)
                     │
                     └── expected = yes_no (State 4)
                           → RUN Model 1
                           → handle (see below)


================================================================
FREE TEXT HANDLING — STATE 1 (stage: identify)
================================================================

  Why Model 1 skipped:
  Reply like "physics exam" has no command structure.
  We know we are waiting for a task identifier.

  User replies: anything

  → treat entire reply as task_name identifier
  → merge into pending entities as task_name
  → AI server clears Redis
  → re-enter handler from STEP 1
  → handler now has identifier → queries DB → continues


================================================================
FREE TEXT HANDLING — STATE 3 (stage: what_to_update)
================================================================

  Why Model 1 skipped:
  Reply like "change priority to high" or "move to Tuesday"
  is a fragment — Model 1 might misclassify.
  We know exactly what we are waiting for.

  User replies: anything describing what to change

  → pass reply through NER to extract update entities:
      new_date, new_time, new_priority,
      new_status, new_duration, new_title

  → merge extracted update fields into pending entities
  → AI server clears Redis
  → re-enter handler from STEP 5 (check update fields)
    with task_id already known

  If NER extracts nothing useful:
  → Redis stays (TTL resets)
  → Gemini: "I didn't catch that. You can say things
             like 'priority to high', 'move to Tuesday',
             or 'mark as complete', Ali."
  → STOP


================================================================
NUMBER HANDLING — STATE 2 (stage: identify)
================================================================

  Why Model 1 runs first:
  "1" or "2" could be a task name or other input.
  Model 1 confirms it is confirmation intent first.

  Model 1 runs:

    → command / multiple_command:
        Redis stays (TTL resets)
        Gemini: "I'm still waiting for your choice.
                 Say cancel to stop."
        STOP

    → general / out_of_scope:
        Redis stays (TTL resets)
        Gemini: "Pick a number from the list, Ali."
        STOP

    → confirmation → proceed:

  Valid number (1 to N):
  → get selected task = tasks[number - 1]
  → update Redis:
      task_id  = selected_task_id
      task     = selected_task
      stage    = "what_to_update" (if no update fields yet)
             OR = "confirm" (if update fields already known)
      remove task_ids and tasks arrays
  → if update fields already in entities:
      jump to STEP 5 (validate) then STEP 7 (confirm)
  → if no update fields:
      set expected_response = "free_text"
      Gemini: "What would you like to change about
               [task name], Ali?"
      STOP

  Number out of range:
  → Redis stays (TTL resets)
  → Gemini: "That number is not on the list, Ali.
             Pick between 1 and [N]."
  → STOP

  Anything else:
  → Redis stays (TTL resets)
  → Gemini: "Pick a number from the list, Ali."
  → STOP


================================================================
YES/NO HANDLING — STATE 4 (stage: confirm)
================================================================

  Why Model 1 runs first:
  "yes" could begin a new command.
  Model 1 confirms it is confirmation intent first.

  Model 1 runs:

    → command / multiple_command:
        Redis stays (TTL resets)
        Gemini: "I'm still waiting — should I go ahead
                 with the update? Yes or no, Ali."
        STOP

    → general / out_of_scope:
        Redis stays (TTL resets)
        Gemini: "Just a yes or no, Ali."
        STOP

    → confirmation → proceed:

  YES keywords:
  yes / yeah / yep / sure / go ahead / confirm / ok / do it
  → AI server clears Redis
  → jump to STEP 8 of update handler (perform update)

  NO keywords:
  no / nope / nah / don't / leave it / keep it
  → AI server clears Redis
  → Gemini: "No problem, Physics exam stays as it is."
  → STOP

  Unrecognised:
  → Redis stays (TTL resets)
  → Gemini: "Just a yes or no, Ali."
  → STOP


================================================================
CROSS CUTTING CASES (apply to ALL states)
================================================================

CANCEL — always checked first
────────────────────────────────────────────────────────────
  cancel / stop / abort / never mind / forget it /
  forget that / leave it / discard / no cancel

  → AI server clears Redis
  → Gemini: "No problem Ali, nothing was changed."
  → STOP


NEW COMMAND WHILE PENDING — yes_no and number only
────────────────────────────────────────────────────────────
  (free_text states skip Model 1 — not applicable there)

  Model 1 returns command / multiple_command:
  → Redis stays (TTL resets)
  → Gemini: "I'm still waiting for your reply, Ali.
             Say cancel if you want to start fresh."
  → STOP


TTL EXPIRY — all states
────────────────────────────────────────────────────────────
  User silent for 300 seconds
  → Redis auto-expires
  → next input starts pipeline fresh
  → no message needed


================================================================
GEMINI REPLY GUIDELINES FOR UPDATE CONTEXT MANAGER
================================================================

  WRONG — never use:
  × "Invalid input."
  × "Please specify the update field."
  × "Task updated successfully."
  × "Confirmation required."

  CORRECT — what Gemini generates:
  ✓ "Which task would you like to update, Ali?"
  ✓ "I found 3 tasks. Which one did you mean?"
  ✓ "What would you like to change about
     Physics exam, Ali?"
  ✓ "Change Physics exam priority to high. Confirm?"
  ✓ "Done Ali — Physics exam priority is now high."
  ✓ "No problem, nothing was changed."


================================================================
STAGE TRANSITION SUMMARY
================================================================

  stage: identify
    → free_text reply → re-enter STEP 1 (find task again)
    → number reply    → task selected → jump to:
                          no update fields: what_to_update
                          update fields known: confirm

  stage: what_to_update
    → free_text reply → NER extracts update fields
                      → re-enter STEP 5 (validate fields)

  stage: confirm
    → yes → STEP 8 (perform update)
    → no  → cancel, clear Redis

SUMMARY TABLE
================================================================

  State │ stage           │ expected  │ Model 1? │ on valid reply
  ──────┼─────────────────┼───────────┼──────────┼──────────────────────────────
  1     │ identify        │ free_text │ NO       │ treat as task_name → STEP 1
  2     │ identify        │ number    │ YES      │ pick task → what_to_update or confirm
  3     │ what_to_update  │ free_text │ NO       │ NER extract fields → STEP 5
  4     │ confirm         │ yes_no    │ YES      │ yes → STEP 8 | no → cancel
